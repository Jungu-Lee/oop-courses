class 클래스와_인스턴스:# 1. 설계도와 실체

핵심 개념

  • 클래스(Class): 객체를 만들기 위한 설계도. 속성(데이터)과 메서드(행위)를 정의한다.
  • 인스턴스(Instance): 클래스를 기반으로 메모리에 실제로 생성된 객체. 하나의 클래스에서 서로 독립적인 인스턴스를 여러 개 만들 수 있다.
  • __init__: 인스턴스 생성 시 자동 호출되는 초기화 메서드. 실제 메모리 할당은 __new__가 담당하고, __init__은 만들어진 객체의 초기값 세팅을 맡는다.
  • self: 메서드가 호출될 때 그 인스턴스 자신을 가리키는 첫 번째 매개변수. p.introduce()는 내부적으로 Person.introduce(p)와 같다.

상황: 학교 정보 시스템에서 "사람"을 표현해야 한다. 사람은 이름과 나이라는 데이터를 가지고, 자기소개를 할 수 있어야 한다. 또한 객체가 생성되는 두 단계(메모리 할당 → 초기화)를 눈으로 확인할 수 있도록 만들어보자. 이 요구사항을 클래스로 설계하면 다음과 같다.

class Person:
    def __new__(cls, *args, **kwargs):
        print("1) __new__ 호출: 메모리에 객체 할당")
        return super().__new__(cls)     # 만들어진 객체를 반환해야 __init__이 호출됨

    def __init__(self, name, age):
        print("2) __init__ 호출: 객체 초기화")
        self.name = name        # 인스턴스 변수
        self.age = age

    def introduce(self):
        print(f"저는 {self.name}, {self.age}살입니다.")

p1 = Person("홍길동", 17)
# 1) __new__ 호출: 메모리에 객체 할당
# 2) __init__ 호출: 객체 초기화
p1.introduce()              # 저는 홍길동, 17살입니다.
참고: 평소에는 __new__를 직접 작성할 필요가 없다(생략하면 object.__new__가 자동 사용). 불변 자료형(int, str, tuple)을 상속해 커스터마이징하거나, 섹션 3의 싱글톤 패턴처럼 인스턴스 생성 자체를 제어할 때만 오버라이딩한다.

__new__(cls, *args, **kwargs) — 매개변수를 이렇게 받는 이유

① cls를 받는 이유: __new__가 호출되는 시점에는 아직 인스턴스가 존재하지 않는다. self는 "이미 만들어진 객체"를 가리키지만, __new__는 "그 객체를 지금부터 만들어야 하는" 시점의 메서드이므로 참조할 self가 없다. 대신 "어떤 클래스의 인스턴스를 만들 것인가"를 나타내는 cls가 필요하다 — @classmethod가 cls를 받는 것과 같은 원리이며, 상속 시 자식 클래스에서 호출되면 cls에 자식 클래스가 들어와 자식 인스턴스가 만들어지도록 보장한다. (주의: cls가 클래스 자체를 새로 만드는 것이 아니다 — Person 같은 클래스는 class Person: ... 문이 실행될 때 이미 만들어져 있고, cls는 그중 "어느 클래스의 인스턴스를 생성할지"를 가리킬 뿐이다.)

② *args, **kwargs를 받는 이유: Person("홍길동", 17)을 호출하면, 파이썬 내부적으로는 다음과 같이 동작한다.

obj = Person.__new__(Person, "홍길동", 17)   # ① 생성자 인자가 __new__에도 그대로 전달됨
Person.__init__(obj, "홍길동", 17)           # ② __init__에도 동일한 인자가 전달됨

즉 생성자에 전달한 인자들이 __init__뿐 아니라 __new__에도 그대로 전달된다. 만약 __new__가 cls만 받도록 정의했다면 다음처럼 오류가 난다.

class Person:
    def __new__(cls):              # *args, **kwargs 없음
        return super().__new__(cls)
    def __init__(self, name, age):
        self.name, self.age = name, age

p1 = Person("홍길동", 17)
# TypeError: Person.__new__() takes 1 positional argument but 3 were given

__init__이 몇 개의 인자를 받든 호출이 깨지지 않도록, __new__는 *args, **kwargs로 "무엇이 오든 다 받아주는" 유연한 시그니처를 갖춰야 한다. 다만 메모리 할당 자체에는 name, age 값이 필요 없으므로(실제 사용처는 __init__), __new__는 호출 시그니처를 맞추기 위해서만 이 인자들을 받아두고 실제로는 사용하지 않은 채 super().__new__(cls)에는 cls만 넘긴다.

정리: cls는 "아직 없는 self 대신, 어떤 클래스의 인스턴스를 만들어야 하는지"를, *args, **kwargs는 "__init__에 어떤 인자가 전달되든 __new__ 호출이 깨지지 않도록" 하기 위한 것이다.

큰 그림으로 보기: 클래스 정의부터 객체 생성까지

상황: 이번엔 "학생"을 표현해야 한다. 모든 학생은 같은 학교(대구과학고) 소속이라는 공통 정보를 갖지만, 이름과 학년은 학생마다 다르다. 또한 신입생은 항상 1학년으로 간편하게 생성할 수 있는 방법도 있으면 좋겠다. 클래스 하나 안에는 공유되는 것(클래스 변수, 클래스 메서드)과 인스턴스마다 만들어지는 것(객체 변수, 객체 메서드가 다루는 데이터)이 함께 정의된다. 다음 Student 예제로 여섯 개념의 관계를 한 번에 살펴보자.

class Student:                        # ① 클래스 정의
    school = "대구과학고"              # ⑤ 클래스 변수 — 모든 인스턴스가 공유

    def __init__(self, name, grade):
        self.name = name               # ③ 객체(인스턴스) 변수
        self.grade = grade             #    — 인스턴스마다 독립적으로 저장

    def introduce(self):              # ④ 객체(인스턴스) 메서드
        print(f"{self.name} ({self.grade}학년) - {self.school}")

    @classmethod
    def new_freshman(cls, name):       # ⑥ 클래스 메서드 — 대안 생성자
        return cls(name, 1)             #    항상 1학년으로 생성

s1 = Student("민준", 2)                # ② 일반 생성자로 객체 생성
s2 = Student.new_freshman("도윤")       # ② 클래스 메서드로 객체 생성

s1.introduce()   # 민준 (2학년) - 대구과학고
s2.introduce()   # 도윤 (1학년) - 대구과학고

print(s1.school)              # 대구과학고 — s1에 school이 없으므로 클래스로 위임
print(s2.school)              # 대구과학고 — s2도 동일하게 위임
print(s1.school is s2.school)   # True — 둘 다 클래스의 '같은 객체'를 참조

왜 self를 굳이 매개변수로 받는가?

파이썬은 "명시적인 것이 암묵적인 것보다 낫다"(PEP 20, The Zen of Python)는 설계 철학을 따른다. Java·C++의 this처럼 인스턴스 자신에 대한 접근을 문법적으로 숨겨 자동 주입하는 대신, 파이썬은 이를 눈에 보이는 첫 번째 매개변수로 명시하게 만든다.

실제로 클래스의 메서드는 특별한 문법이 아니라, 첫 번째 인자로 인스턴스를 받는 평범한 함수일 뿐이다. d1.bark()는 인터프리터가 내부적으로 Dog.bark(d1)로 변환해 실행하는 것이며, self가 매개변수로 명시되어 있기 때문에 이 변환이 투명하고 예측 가능하다.

class Dog:
    def bark(self):
        print(f"{self.name}가 짖습니다")

d1 = Dog()
d1.name = "바둑이"

d1.bark()           # 이것과
Dog.bark(d1)         # 이것은 완전히 동일하다

이 설계는 실질적인 이점을 준다.

  • 함수와 메서드를 같은 문법으로 다룰 수 있다 — self가 숨겨진 규칙이 아니라 그냥 "첫 번째 매개변수"이므로, 클래스 밖의 평범한 함수를 메서드로 그대로 등록할 수도 있다.
  • 이름 자체는 관례일 뿐, 언어가 강제하지 않는다 — self 대신 다른 이름을 써도 문법 오류는 나지 않는다(다만 관례를 어기면 다른 개발자가 혼란스러우므로 항상 self를 쓴다).
  • @staticmethod, @classmethod와 일관된 틀로 설명된다 — "인스턴스 메서드는 self를, 클래스 메서드는 cls를 받고, 정적 메서드는 아무것도 받지 않는다"는 규칙이 모두 "첫 번째 매개변수로 무엇이 자동 전달되는가"라는 하나의 원리로 통일된다.
def bark(self):
    print(f"{self.name}가 짖습니다")

class Dog:
    speak = bark   # 클래스 밖의 평범한 함수를 메서드로 등록 가능
                   # — self가 마법이 아니라 매개변수이기 때문에 가능한 일
정리: 파이썬은 "인스턴스 자신에 대한 접근"조차 마법으로 숨기지 않고, 이미 존재하는 "매개변수 전달"이라는 언어 규칙 하나로 설명하기 위해 self를 첫 번째 인자로 명시적으로 받게 설계했다.

클래스와 인스턴스의 메모리 구조

클래스는 메서드(행위)를 한 번만 저장하고, 각 인스턴스는 자신의 데이터(상태)만 독립적으로 갖는다. 인스턴스에서 속성을 찾으면 자기 __dict__를 먼저 보고, 없으면 클래스로 거슬러 올라가 메서드를 찾는다 — 이것이 p1.introduce()가 동작하는 원리다.

왜 OOP인가? 알고리즘 문제 풀이(절차적 스타일)에서는 전역 변수와 함수만으로 충분하지만, 시뮬레이션·GUI·팀 프로젝트처럼 상태(state)가 많고 오래 유지되는 프로그램에서는 데이터와 행위를 객체 단위로 묶어야 결합도를 낮추고 유지보수가 가능해진다.

1-1클래스와 인스턴스의 관계를 붕어빵 틀·붕어빵에 비유할 때, 설계도(틀)와 실체(붕어빵)는 각각 무엇에 해당하는가?

정답 보기
설계도(틀) = 클래스, 실체(붕어빵) = 인스턴스. 클래스는 코드상에 하나만 정의되지만, 그 클래스를 바탕으로 서로 독립적인 인스턴스를 원하는 만큼 만들 수 있다.

1-2다음 코드에서 d1.bark()를 호출했을 때 self가 가리키는 대상은? 만약 Dog.bark(d1)처럼 직접 호출한다면 결과가 같은가?

class Dog:
    def __init__(self, name): self.name = name
    def bark(self): print(f"{self.name}가 짖습니다")

d1 = Dog("바둑이")
d1.bark()
정답 보기
self는 호출한 인스턴스 자신인 d1을 가리킨다. d1.bark()는 파이썬 내부적으로 Dog.bark(d1)과 동일하게 해석되므로, 직접 Dog.bark(d1)로 호출해도 결과는 같다 (바둑이가 짖습니다).

1-3__new__와 __init__ 중 실제로 메모리에 객체를 할당하고 반환하는 것은 무엇이며, 두 메서드는 어떤 순서로 호출되는가?

정답 보기
실제 생성자 역할(메모리 할당·객체 반환)은 __new__가 담당한다. 호출 순서는 __new__가 먼저 실행되어 객체를 생성·반환하고, 그 객체가 self로 __init__에 전달되어 초기값을 세팅한다. (__new__가 해당 클래스의 인스턴스를 반환하지 않으면 __init__은 아예 호출되지 않는다.)

1-4다음 코드의 출력 결과를 예측하시오.

class Person:
    def __init__(self, name): self.name = name

p1 = Person("민수")
p2 = Person("지훈")
p1.name = "철수"
print(p1.name, p2.name)
print(p1 is p2)
정답 보기
철수 지훈 / False. p1과 p2는 서로 독립된 __dict__(메모리)를 가지므로 한쪽의 속성을 바꿔도 다른 쪽에는 영향이 없다. is는 정체성(메모리 주소) 비교이므로 서로 다른 두 객체는 항상 False다.

1-5(다이어그램 연계) 메서드는 클래스에 한 번만 저장되어 모든 인스턴스가 공유한다고 배웠다. 만약 p1.introduce = "hi"처럼 인스턴스에 같은 이름의 속성을 대입하면, 이후 p1.introduce()를 호출하면 어떻게 되는가? p2.introduce()는 영향을 받는가?

정답 보기
이제 p1.introduce는 함수가 아니라 문자열 "hi"를 가리키므로(인스턴스 변수가 클래스 메서드를 가리는 shadowing), p1.introduce()를 호출하면 TypeError: 'str' object is not callable이 발생한다. p2는 자신만의 introduce 속성이 없으므로 여전히 클래스의 메서드를 그대로 참조해 정상 동작한다.

① 캡슐화 (Encapsulation)

데이터와 메서드를 하나로 묶고, 외부의 직접 접근을 제한(정보 은닉)한다. 파이썬은 강제적 접근 제어자 대신 네이밍 관례를 쓴다.

표기의미비고
namePublic자유롭게 접근
_nameProtected (관례)"내부용" 신호일 뿐 강제성 없음
__namePrivate네임 맹글링(_클래스명__name)으로 직접 접근 차단

파이썬다운 캡슐화는 @property를 쓴다 — 속성처럼 읽고 쓰되, setter에서 검증 로직을 끼워 넣는다.

상황: 회원 시스템에서 사용자 이름을 다뤄야 한다. 그런데 이름이 한 글자짜리로 잘못 입력되는 것을 막고 싶다. 이름을 아무나 마음대로 바꾸지 못하게 하면서도, 바꾸려는 시도가 있을 때는 항상 검증을 거치도록 설계해야 한다.

class User:
    def __init__(self, name): self._name = name

    @property
    def name(self): return self._name

    @name.setter
    def name(self, new):
        if len(new) < 2: raise ValueError("이름은 2글자 이상")
        self._name = new

② 상속 (Inheritance)

  • 부모 클래스의 속성·메서드를 자식이 물려받는다 (IS-A 관계).
  • super().__init__(...)으로 부모의 초기화를 호출한다.
  • 오버라이딩(Overriding): 물려받은 메서드를 자식이 재정의.

상황: 동물원 관리 프로그램에서 여러 동물을 표현해야 한다. 모든 동물은 이름을 갖지만, 우는 소리는 동물마다 다르다. "이름 저장"이라는 공통 로직을 매번 반복해서 작성하고 싶지 않다.

class Animal:
    def __init__(self, name): self.name = name
    def speak(self): return "..."

class Cat(Animal):                      # Cat IS-A Animal
    def __init__(self, name, color):
        super().__init__(name)           # 부모의 초기화 재사용
        self.color = color
    def speak(self):                    # 오버라이딩
        return f"{self.name}: 야옹"

print(Cat("나비", "검정").speak())   # 나비: 야옹

super().__init__()은 반드시 호출해야 하는가?

문법적으로 강제되지는 않지만, 실무에서는 거의 항상 호출해야 한다. 자식이 __init__을 오버라이딩하지 않으면 부모의 __init__이 자동으로 그대로 쓰이지만, 오버라이딩하는 순간 파이썬은 부모의 __init__을 자동으로 호출해주지 않는다 — 오버라이딩은 자동 병합이 아니라 완전 대체다.

# 사례 ① 오버라이딩 자체를 안 하면 → 별도 호출 불필요 (부모 __init__ 그대로 사용)
class Cat(Animal):
    pass

c = Cat("나비")
print(c.name)                # 나비 — Animal.__init__이 자동으로 쓰임


# 사례 ② __init__을 오버라이딩했는데 super()를 빼먹으면 → 위험
class Cat(Animal):
    def __init__(self, name, color):
        self.color = color        # super().__init__(name)이 없음
                                   # → self.name이 아예 생성되지 않음!

c = Cat("나비", "검정")
c.speak()                         # AttributeError: 'Cat' object has no attribute 'name'


# 사례 ③ 부모 로직 없이 직접 다 설정하면 문법적으로는 동작함
class Cat(Animal):
    def __init__(self, name, color):
        self.name = name           # super() 없이 직접 설정 — 동작은 함
        self.color = color         # 단, 부모 초기화 로직이 바뀌면 여기도 같이 고쳐야 함
                                    # (코드 중복 배제라는 상속의 목적에 어긋남 → 비권장)
다중 상속에서는 더 중요해진다. 믹스인 등 다중 상속 구조에서는 각 클래스가 super().__init__()을 호출해야 MRO를 따라 초기화 체인 전체가 연쇄적으로 실행된다. 중간에 하나라도 호출을 빼먹으면 그 뒤 체인이 끊긴다.
class A:
    def __init__(self):
        print("A init")
        super().__init__()

class B:
    def __init__(self):
        print("B init")
        super().__init__()

class C(A, B):
    def __init__(self):
        print("C init")
        super().__init__()   # MRO를 따라 A.__init__ → B.__init__ 순서로 연쇄 호출

정리: 문법적 강제는 아니지만, __init__을 오버라이딩했다면 super().__init__(...) 호출이 사실상의 표준이다. 생략하면 "부모의 속성이 누락된, 불완전하게 초기화된 객체"가 조용히 만들어져 디버깅하기 까다로운 버그의 원인이 된다.

③ 다형성 (Polymorphism)

같은 이름의 메서드가 객체의 종류에 따라 다르게 동작한다. 파이썬은 덕 타이핑(Duck Typing)을 지원한다: 상속 관계가 없어도 같은 이름의 메서드만 있으면 동일하게 다룰 수 있다.

상황: 여러 동물이 각자 다른 소리를 낸다. 소리를 재생하는 함수를 만들 때, 그 함수가 "지금 들어온 게 개인지 오리인지" 일일이 검사하지 않고도 동작하게 만들고 싶다.

    def speak(self): return "꽥꽥!"

④ 추상화 (Abstraction)

abc 모듈의 추상 클래스(ABC)는 직접 인스턴스화할 수 없고, @abstractmethod가 붙은 메서드를 자식이 반드시 구현하도록 강제한다. 인터페이스를 명세하는 도구다.

상황: 여러 종류의 도형을 다루는 프로그램에서, 도형마다 넓이 계산 공식이 다르다. 앞으로 어떤 도형이 추가되더라도 "넓이 계산 기능을 반드시 구현하도록" 강제하고 싶다 — 깜빡하고 빠뜨리면 프로그램이 그 자리에서 알려주면 좋겠다.

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...              # "넓이를 구할 수 있어야 한다"는 계약만 명세

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self):                  # 구현하지 않으면 Circle도 인스턴스화 불가
        return 3.14159 * self.r ** 2

# Shape()      → TypeError: 추상 클래스는 인스턴스화 불가

클래스 변수 vs 인스턴스 변수

  • 클래스 변수: 클래스 본문에 직접 선언. 모든 인스턴스가 공유.
  • 인스턴스 변수: self.x = .... 인스턴스마다 독립적.
  • 함정: 인스턴스.클래스변수 = 값으로 대입하면 클래스 변수가 바뀌는 게 아니라 같은 이름의 인스턴스 변수가 새로 생겨 클래스 변수를 가린다(shadowing).

상황: 자동차 생산 관리 프로그램을 만든다. 같은 모델의 자동차는 모두 바퀴 개수(4개)가 같지만, 색상은 차량마다 다르다. 모든 차량에 공통되는 값과, 차량마다 따로 저장해야 하는 값을 구분해서 관리하고 싶다.

class Car:
    wheels = 4                     # 클래스 변수: 모든 인스턴스가 공유
    def __init__(self, color):
        self.color = color         # 인스턴스 변수: 객체마다 독립

c1, c2 = Car("red"), Car("blue")
Car.wheels = 6                     # 클래스 변수 변경 → 모두에 반영

c1.wheels = 3                      # ⚠ 클래스 변수 수정이 아니라
                                   #   c1에만 있는 인스턴스 변수 생성 (shadowing)
print(c1.wheels, c2.wheels)        # 3 6
print(c1.__dict__)                 # {'color': 'red', 'wheels': 3}

class Date:
    def __init__(self, year, month, day):
        self.year, self.month, self.day = year, month, day

    def show(self):                          # ① 인스턴스 메서드
        print(f"{self.year}-{self.month}-{self.day}")

    @classmethod
    def from_string(cls, s):                # ② 대안 생성자 (팩토리)
        y, m, d = map(int, s.split("-"))
        return cls(y, m, d)                  # cls = 호출한 클래스 자신

    @staticmethod
    def is_leap(year):                      # ③ 상태 불필요한 유틸리티
        return year % 4 == 0 and (year % 100 != 0 or year % 400 == 0)

d.show()                                    # 2026-7-18
print(Date.is_leap(2028))                   # True

매직 메서드 (Special Methods)

더블 언더스코어로 감싼 특수 메서드를 구현하면 사용자 정의 클래스가 내장 자료형처럼 동작한다. 파이썬 데이터 모델의 핵심.

메서드연결되는 문법
__repr__ / __str__개발자용 표현 / print() 출력
__add__, __mul__, ...+, * 등 연산자 오버로딩
__eq__, __lt__, ...==, < 비교 (== 기본값은 is 비교)
__len__, __getitem__len(x), x[i], 슬라이싱, for 반복까지 지원

상황: 금액을 다루는 프로그램에서 두 금액을 a + b처럼 자연스럽게 더하고, a == b로 비교하고, 금액 순서대로 정렬도 하고 싶다. 매번 add(a, b) 같은 별도 함수를 만드는 대신, 파이썬 내장 연산자를 그대로 쓸 수 있도록 클래스를 설계해보자.

class Money:
    def __init__(self, won): self.won = won
    def __repr__(self):  return f"Money({self.won})"
    def __add__(self, other):               # + 연산자
        return Money(self.won + other.won)
    def __eq__(self, other):                # == 연산자
        return self.won == other.won
    def __lt__(self, other):                # < 연산자 → sorted()도 가능해짐
        return self.won < other.won

a, b = Money(5000), Money(3000)
print(a + b)                    # Money(8000)   ← __add__ + __repr__
print(a == Money(5000))         # True          ← __eq__ 없으면 False (is 비교)
print(sorted([a, b]))           # [Money(3000), Money(5000)]  ← __lt__ 덕분

다중 상속과 MRO

다이아몬드 상속에서 어느 부모의 메서드를 먼저 찾을지는 MRO(Method Resolution Order)가 결정한다 — C3 선형화 알고리즘 기반. 규칙 세 가지: ⑴ 자식이 부모보다 먼저, ⑵ class D(B, C)의 나열 순서 유지, ⑶ 부모들의 순서가 자식에서 뒤집히지 않음. D.mro()로 확인할 수 있다.

class A:
    def hello(self): print("A")
class B(A):
    def hello(self): print("B")
class C(A):
    def hello(self): print("C")
class D(B, C):                # 다이아몬드:  A ← B, A ← C, (B,C) ← D
    pass

D().hello()                    # B  — MRO에서 B가 C보다 앞
print(D.mro())
# [D, B, C, A, object]
# 공통 조상 A는 B·C보다 뒤에 '단 한 번만' 등장 — 단순 깊이 우선(B→A→C)이라면

@dataclass

데이터 저장용 클래스의 __init__, __repr__, __eq__를 자동 생성한다. 가변 기본값(리스트 등)은 금지 — 반드시 field(default_factory=list)를 써야 한다.

상황: 쇼핑몰 재고 시스템에서 상품(이름, 가격, 태그 목록)을 저장하는 클래스가 필요하다. 이 클래스는 로직 없이 데이터만 담는 단순한 그릇이라, __init__이나 __repr__ 같은 반복 코드를 직접 작성하고 싶지 않다.

from dataclasses import dataclass, field

@dataclass
class Product:
    name: str
    price: int
    tags: list = field(default_factory=list)  # tags: list = [] 는 ValueError!

p = Product("노트북", 1_500_000)
print(p)                          # Product(name='노트북', price=1500000, tags=[])
print(p == Product("노트북", 1_500_000))   # True — __eq__도 자동 생성

__new__ 와 싱글톤

진짜 생성자는 __new__(메모리 할당·객체 반환)이고 __init__은 초기화만 담당한다. __new__에서 기존 인스턴스를 재사용하면 싱글톤 패턴(인스턴스 1개 보장)을 구현할 수 있다.

상황: 애플리케이션의 환경 설정(테마, 언어 등)은 프로그램 전체에서 단 하나만 존재해야 한다. 여러 곳에서 각자 ConfigManager()를 새로 만들면, 설정 값이 서로 어긋나는 문제가 생길 수 있다. 누가 몇 번을 생성하든 항상 같은 객체를 돌려주도록 만들어야 한다.

class ConfigManager:
    _instance = None

    def __new__(cls):
        if cls._instance is None:                 # 최초 1회만 생성
            cls._instance = super().__new__(cls)
            cls._instance.settings = {}
        return cls._instance                       # 이후엔 기존 객체 반환

c1 = ConfigManager()
c1.settings["theme"] = "dark"
c2 = ConfigManager()                               # 새로 만든 것처럼 보이지만...
print(c2.settings["theme"])    # dark — 같은 객체를 공유
print(c1 is c2)                # True — 메모리 주소가 동일

from abc import ABC, abstractmethod

class DiscountPolicy(ABC):
    @abstractmethod
    def calc(self, price): ...

class Regular(DiscountPolicy):
    def calc(self, price): return price * 0.1

class VIP(DiscountPolicy):
    def calc(self, price): return price * 0.2

class Calculator:
    def __init__(self, policy: DiscountPolicy):
        self.policy = policy               # 새 정책이 생겨도 이 클래스는 수정 불필요
    def apply(self, price):
        return price - self.policy.calc(price)

ISP — 인터페이스를 잘게 나눈다

상황: 공장에서 사람과 로봇이 함께 작업한다. 사람은 일하고 밥도 먹지만, 로봇은 일만 할 뿐 밥을 먹지 않는다. "작업자"라는 범용 인터페이스 하나에 일하기·먹기를 모두 넣으면, 로봇은 쓰지도 않을 "먹기" 기능을 억지로 구현해야 하는 상황이 생긴다.

class Workable(ABC):
    @abstractmethod
    def work(self): ...

    @abstractmethod
    def eat(self): ...

    def work(self): ...
    def eat(self): ...

DIP — 추상화에 의존한다

상황: 알림 시스템에서 지금은 이메일로만 발송하지만, 곧 SMS 발송도 추가해야 한다. 알림 서비스 코드가 "이메일 발송기"라는 구체적인 구현에 직접 묶여 있으면, 발송 수단을 바꾸거나 추가할 때마다 알림 서비스 코드 자체를 고쳐야 하는 문제가 생긴다.

class MessageSender(ABC):                   # 추상화 (인터페이스)
    @abstractmethod
    def send(self, msg): ...

class EmailSender(MessageSender):
    def send(self, msg): print(f"이메일: {msg}")

class SMSSender(MessageSender):
    def send(self, msg): print(f"SMS: {msg}")

class NotificationService:                  # 고수준 모듈
    def __init__(self, sender: MessageSender):  # 구체 클래스가 아닌
        self.sender = sender                    # 추상화에 의존 (의존성 주입)
    def notify(self, msg):
        self.sender.send(msg)

NotificationService(EmailSender()).notify("안녕하세요")  # 이메일: 안녕하세요
NotificationService(SMSSender()).notify("안녕하세요")    # SMS: 안녕하세요
주의: 원칙과 패턴은 목적이 아니라 수단이다. 클래스 분리가 오히려 직관성을 해치는 과잉 설계(Over-engineering)는 감점 대상임을 기억하자.

Q2@property로 검증이 있는 캡슐화 구현 캡슐화property★

BankAccount 클래스를 작성하시오. 요구사항:

  1. 잔액은 외부에서 직접 대입할 수 없도록 은닉한다.
  2. balance 프로퍼티로 잔액을 읽을 수 있다.
  3. deposit(amount), withdraw(amount) 메서드를 제공하되, 음수 입금과 잔액 초과 출금 시 ValueError를 발생시킨다.
모범 답안 및 해설 
class BankAccount:
    def __init__(self, balance=0):
        self._balance = balance

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        if amount <= 0: raise ValueError("입금액은 양수여야 합니다")
        self._balance += amount

    def withdraw(self, amount):
        if amount > self._balance: raise ValueError("잔액 부족")
        self._balance -= amount

def total_area(shapes):
    total = 0
    for s in shapes:
        if isinstance(s, Circle):
            total += 3.14 * s.radius ** 2
        elif isinstance(s, Rectangle):
            total += s.w * s.h
    return total
모범 답안 및 해설 
from abc import ABC, abstractmethod
import math

class Shape(ABC):
    @abstractmethod
    def area(self): ...

class Circle(Shape):
    def __init__(self, r): self.r = r
    def area(self): return math.pi * self.r ** 2

class Rectangle(Shape):
    def __init__(self, w, h): self.w, self.h = w, h
    def area(self): return self.w * self.h

def total_area(shapes):
    return sum(s.area() for s in shapes)   # 수정 불필요

각 도형이 자신의 넓이 계산 책임을 갖도록 동적 바인딩으로 분기를 제거했다. 새 도형은 Shape를 상속해 area()만 구현하면 된다 → 개방-폐쇄 원칙(OCP). 단일 책임 원칙(SRP)도 함께 개선된다.

Q8@classmethod 대안 생성자 만들기 classmethod팩토리★★

2차원 격자 위 입자를 나타내는 Particle(x, y, mass) 클래스가 있다. 다음 두 대안 생성자를 @classmethod로 추가하시오.

  1. Particle.from_string("3,4,1.5") — CSV 문자열 파싱
  2. Particle.origin(mass) — 원점 (0, 0)에 생성

또한 @staticmethod가 아닌 @classmethod를 써야 하는 이유를, 이 클래스를 상속한 자식 클래스 관점에서 설명하시오.

모범 답안 및 해설 
class Particle:
    def __init__(self, x, y, mass):
        self.x, self.y, self.mass = x, y, mass

    @classmethod
    def from_string(cls, s):
        x, y, m = s.split(",")
        return cls(float(x), float(y), float(m))

    @classmethod
    def origin(cls, mass):
        return cls(0, 0, mass)

이유: cls는 호출한 클래스 자신이 바인딩된다. class ChargedParticle(Particle)이 ChargedParticle.origin(1.0)을 호출하면 cls == ChargedParticle이므로 자식 인스턴스가 만들어진다. 클래스명을 하드코딩한 @staticmethod 버전(return Particle(...))은 상속 시 항상 부모 인스턴스를 반환하는 버그를 만든다.

Q10종합 설계 — 절차적 시뮬레이터의 OOP 전환 종합전략 패턴추상화★★★

다음은 절차적으로 작성된 입자 시뮬레이터의 일부다. 새로운 입자 종류가 추가될 때마다 조건문과 전역 변수가 늘어나는 구조다.

particles = []          # [type, x, v] 리스트의 리스트
GRAVITY = 9.8

def update(dt):
    for p in particles:
        if p[0] == "normal":
            p[2] -= GRAVITY * dt
            p[1] += p[2] * dt
        elif p[0] == "bouncy":
            p[2] -= GRAVITY * dt
            p[1] += p[2] * dt
            if p[1] < 0: p[1], p[2] = 0, -p[2] * 0.9
        elif p[0] == "frozen":
            pass

다음 요구사항을 만족하도록 객체지향 구조로 재설계하시오 (클래스 다이어그램을 먼저 그린 뒤 코드 작성 권장).

  1. 추상 클래스 Particle이 공통 상태(x, v)와 인터페이스 update(dt)를 정의한다.
  2. NormalParticle, BouncyParticle, FrozenParticle이 각자의 운동을 구현한다.
  3. Simulator 클래스가 입자 목록과 중력 상수를 캡슐화하고(전역 변수 제거), step(dt)에서 조건문 없이 모든 입자를 갱신한다.
  4. 새로운 종류 "저항 입자"(속도에 −0.1·v의 공기저항 가속도 추가)를 기존 코드 수정 없이 클래스 추가만으로 도입해 보이시오.
모범 답안 및 해설 
from abc import ABC, abstractmethod

class Particle(ABC):
    def __init__(self, x=0.0, v=0.0):
        self.x, self.v = x, v

    @abstractmethod
    def update(self, dt, g): ...

class NormalParticle(Particle):
    def update(self, dt, g):
        self.v -= g * dt
        self.x += self.v * dt

class BouncyParticle(NormalParticle):
    def update(self, dt, g):
        super().update(dt, g)          # 공통 낙하 로직 재사용
        if self.x < 0:
            self.x, self.v = 0, -self.v * 0.9

class FrozenParticle(Particle):
    def update(self, dt, g): pass

class Simulator:
    def __init__(self, gravity=9.8):
        self._particles = []           # 전역 변수 → 인스턴스 상태로 캡슐화
        self._g = gravity

    def add(self, p: Particle):
        self._particles.append(p)

    def step(self, dt):
        for p in self._particles:
            p.update(dt, self._g)      # 동적 바인딩 — 조건문 없음

# (4) 기존 코드 수정 없이 확장 — OCP
class DragParticle(Particle):
    def update(self, dt, g):
        self.v += (-g - 0.1 * self.v) * dt
        self.x += self.v * dt

평가 관점 (아키텍처 채점 기준):

  • 추상화 — 입자를 상태(x, v) + 행위(update)를 지닌 객체로 모델링했는가.
  • 다형성 — Simulator.step이 타입 분기 없이 동적 바인딩만으로 동작하는가.
  • 캡슐화 — 전역 상태(particles, GRAVITY)가 Simulator 내부로 은닉되었는가.
  • OCP — 새 입자를 클래스 추가만으로 도입할 수 있는가.
  • 과잉 설계 경계 — 이 규모에서 팩토리·싱글톤 등을 남용하지 않았는가.
